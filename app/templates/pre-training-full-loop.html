We now have all the pieces needed to pre-train the teaching model. The complete program reads and tokenises text, constructs shifted batches, initialises a model, repeatedly optimises its weights, and saves a checkpoint that can be loaded later.

  1. TextRead a plain-text training corpus
  2. BatchesCreate shifted input and target sequences
  3. ModelInitialise the language model with random weights
  4. TrainRepeat forward, loss, backward, and update steps
  5. CheckpointSave the configuration and learned weights

Choose the run configuration

The script exposes the training text, output path, number of epochs, batch size, sequence length, learning rate, and device as command-line arguments. Its defaults deliberately create a very small model that can demonstrate the process on a CPU.

For example, this command runs two passes through the sample text, using batches of four 16-token sequences:

python code/llm/pretrain.py \
    --input code/llm/sample.txt \
    --epochs 2 \
    --batch-size 4 \
    --sequence-length 16

The model configuration and the data loader are then built from those arguments:

torch.manual_seed(1)

model_config = {
    "vocab_size": vocabulary_size(),
    "max_sequence_length": args.sequence_length,
    "model_dim": 32,
    "head_dim": 8,
    "num_heads": 4,
    "hidden_dim": 128,
    "num_layers": 2,
}
model = LanguageModel(**model_config)
batches = create_data_loader(
    args.input,
    args.sequence_length,
    args.batch_size,
)

torch.manual_seed(1) makes the random initial weights and shuffled batches reproducible for this teaching example. The model dimensions are tiny compared with a practical LLM, but the structure of the training loop is the same.

This produces a demonstration, not a useful LLM. The included sample.txt corpus and small model are intentionally chosen so the program is easy to run and inspect. Useful language models require vastly more data, parameters, and computation.

Run the training loop

The orchestration code passes the model, batches, and training settings into the train function:

print(
    f"Training on {len(batches.dataset)} sequences "
    f"in {len(batches)} batches."
)
train(
    model,
    batches,
    args.epochs,
    args.learning_rate,
    args.device,
)

Inside train, each epoch visits every batch once. Every batch produces one optimiser update. The next epoch asks the now-updated model to make predictions over the dataset again, so its loss can continue to fall.

The script uses a fixed epoch count because it is a compact demonstration. Larger runs commonly add validation, learning-rate schedules, periodic checkpoints, and explicit stopping criteria.

Save a reusable checkpoint

Training changes the tensors returned by model.state_dict(). To reconstruct the model later, the checkpoint also stores the dimensions used to create it:

args.output.parent.mkdir(parents=True, exist_ok=True)
torch.save(
    {
        "model_config": model_config,
        "model_state": model.state_dict(),
    },
    args.output,
)
print(f"Saved checkpoint to {args.output}")
What the training checkpoint contains
Checkpoint entry Purpose
model_config Recreates a model with the same vocabulary, sequence length, and layer dimensions
model_state Restores every learned parameter tensor after training

The matching loader constructs the model first, copies in the saved state, switches to evaluation mode, and moves it to the requested device:

def load_training_checkpoint(checkpoint_path, device="cpu"):
    """Load a checkpoint written by pretrain.py."""
    checkpoint = torch.load(
        Path(checkpoint_path).expanduser(),
        map_location="cpu",
        weights_only=True,
    )
    model = LanguageModel(**checkpoint["model_config"])
    model.load_state_dict(checkpoint["model_state"], strict=True)
    model.eval()
    return model.to(device)

Generate with the trained model

The generated checkpoint can be selected instead of the external GPT-2 weights:

python code/llm/generate.py \
    --checkpoint weights/tiny-teaching-model.pth \
    "The lantern"

Generation wraps the prompt in a batch of one, runs the same trainable model, and selects the logits at its final position. The model is therefore trained and used for inference without maintaining two separate architectures.

The output from this tiny checkpoint will usually be poor. That is expected: the purpose of the implementation is to make every stage of pre-training visible, not to conceal it behind the scale and infrastructure required for a practical model.
